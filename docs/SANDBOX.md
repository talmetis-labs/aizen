# The Aizen sandbox

Aizen runs commands a language model wrote and processes a repository can influence. The sandbox
is the layer that decides **what those processes can reach even if they are malicious** — enforced
by kernel mechanisms where the platform has them, and reported honestly where it does not.

This document is the reference: threat model, architecture, mode semantics, the per-platform
capability matrix, configuration, troubleshooting, and the limitations we know about.

## Threat model

Protected against (to the degree the capability matrix below says, per platform):

- commands generated by the model (including a model misled by prompt injection in repository
  files, logs, or tool output);
- shell/script indirection: a command that writes a script and runs it, build scripts, test
  scripts, npm lifecycle hooks, Makefiles, Cargo build scripts;
- reading credentials outside the workspace (`~/.ssh`, `~/.aws`, `~/.aizen`, browser profiles,
  cloud credential stores);
- writing or deleting files outside the workspace;
- undeclared network access;
- child/grandchild/background processes escaping cleanup;
- fork bombs, runaway memory, output floods;
- privilege escalation via setuid/capabilities (Linux);
- repository persistence surfaces: `.git/hooks`, fsmonitor daemons, credential helpers are
  disabled for every internal git invocation Aizen makes;
- a sub-agent, workflow, cron job, or hosted bot raising its own privileges — the mode is
  process-global and user-controlled; children inherit, never escalate.

Explicitly **not** protected against:

- kernel exploits;
- an already-compromised user account or machine;
- secrets the user placed **inside** the workspace (the workspace is read-write by definition);
- a human approving a harmful command after reading it.

## Approval is not the sandbox

The two layers answer different questions:

- **Approval** (`ask`/`smart`/`yolo`, plus the `cmd_guard` hard floor): *did the user agree to run
  this command?* `/yolo` skips the approval prompt. It does not touch the sandbox: it grants no
  secrets, no network, no out-of-workspace writes.
- **Sandbox**: *given that the command runs, what can it reach?* Even a fully approved command
  runs without Aizen's secrets in its environment, and — where the kernel backend exists —
  cannot write outside the workspace or open network connections it was not granted.

Execution order for every guarded command: parse → `cmd_guard` hard floor → capability
computation (`network: true` is an escalation and always surfaces) → approval → sandbox policy
resolution → backend capability check (strict fails closed here) → spawn under the sandbox →
audit line.

## Architecture

```
src/sandbox/
  mod.rs           SandboxMode, CommandOrigin, process-wide mode
  policy.rs        config section, env scrubbing, filesystem roots
  request.rs       SandboxRequest — one spawn's worth of intent
  capabilities.rs  the honest per-platform capability probe
  runner.rs        the ONE place a sandboxed Command is built
  audit.rs         owner-only JSONL audit log
  backend/
    guarded.rs     software floor: env scrub, private temp (all platforms)
    linux.rs       Landlock + seccomp + rlimits + no_new_privs
    windows.rs     Job Object limits + containment
    macos.rs       Seatbelt (sandbox-exec) profile
```

Every model- or repository-influenced spawn goes through `runner::prepare_std` /
`prepare_tokio`: `shell_run`, `process start`, the verify gate, LSP servers, MCP stdio servers,
custom-command `` !`cmd` `` expansion, the REPL `!cmd` escape, and hosted-bot `/sh`. Call sites
choose a `CommandOrigin`; the model only ever supplies command strings. There is no
`bypass_sandbox` flag, and `InternalTrusted` is constructible only from Aizen's own code with a
literal reason recorded in the audit log.

Internal spawns that do **not** go through the runner, with the reason they are trusted: git
plumbing (`gitx`, hardened as described above — Aizen-controlled argv over untrusted repo data),
`schtasks`/`crontab` registration (fixed argv), `systemctl` service management (fixed argv),
opening the OAuth browser (`start`/`open`/`xdg-open` with a provider URL), and the `ioreg`
device probe on macOS. None of them execute model-supplied strings.

## Modes

| mode | meaning |
|---|---|
| `auto` (default) | strongest available backend. Interactive sessions fall back to `guarded` when no kernel backend exists — warned once per session. **Unattended runs (cron, hosted bots) fail closed** instead, unless `sandbox.allow_guarded_fallback = true`. |
| `strict` | kernel enforcement or refusal. If the platform cannot kernel-enforce the filesystem policy (and network deny, when denying), the spawn is refused before it starts. Never self-downgrades; `/yolo` and remote approvals cannot weaken it. |
| `guarded` | software guards only: approval, `cmd_guard`, env scrubbing, private temp, timeouts, tree-kill, and the resource ceilings the OS offers. Reported as software, never as a kernel sandbox. |
| `off` | the sandbox subsystem stands down: children inherit the full environment and no resource ceilings are applied. The `cmd_guard` hard floor, approval, process-tree containment, timeouts, and the audit log still apply. User-only — no model output can select it. |

Set the mode with `--sandbox <mode>`, `AIZEN_SANDBOX=<mode>`, `/sandbox <mode>` in the REPL, or
`"sandbox": { "mode": "…" }` in `~/.aizen/cli-config.json` (that order wins).

## Platform capability matrix

`aizen sandbox status` prints the live matrix for your machine; this table is the design-level
summary. Levels: **enforced** (kernel), **partial** (kernel for part of the surface),
**advisory** (software checks only), **unavailable**.

| capability | Linux | Windows | macOS |
|---|---|---|---|
| filesystem read confinement | **enforced** (Landlock, 5.13+) | advisory | **partial** (credential dirs denied; other reads allowed) |
| filesystem write confinement | **enforced** (Landlock) | advisory | **enforced** (Seatbelt) |
| network deny | **enforced** (seccomp: `socket(AF_INET/AF_INET6)` → `EACCES`) | **unavailable** | **enforced** (Seatbelt) |
| env isolation (secret scrub) | **enforced** | **enforced** | **enforced** |
| process-tree containment | **enforced** (process groups) | **enforced** (Job Object, kill-on-close) | **enforced** |
| resource limits | **enforced** (rlimits) | **enforced** (Job Object: process count, memory, CPU time) | **partial** (rlimits; `RLIMIT_AS` unreliable on XNU) |

Consequences worth spelling out:

- **On Windows, `strict` refuses every spawn.** There is no unprivileged kernel filesystem or
  network sandbox without an AppContainer backend, which is not implemented (see Known
  limitations). `auto` degrades to `guarded` with a warning; that is the honest ceiling today.
- On Linux kernels without Landlock (< 5.13 or disabled), `auto` degrades and `strict` refuses.
- macOS is probed at runtime (`/usr/bin/sandbox-exec` present and executable); a host without it
  reports `guarded`.

## Filesystem policy

Default profile: **workspace-write**.

- read+write: the workspace root, the command's `cwd`, a **private per-run temp directory**
  (`TMP`/`TEMP`/`TMPDIR` point at it; deleted when the run's bookkeeping is dropped), and the
  build-cache homes toolchains write to as a matter of course (`$CARGO_HOME`/`~/.cargo`,
  `~/.npm`, `$XDG_CACHE_HOME`/`~/.cache`);
- read+execute: system and toolchain roots (`/usr`, `/etc`, `/opt`, `~/.rustup`, `~/.gitconfig`,
  `~/.config/git`, …);
- denied (kernel-denied on Linux by omission from the allow-list; explicit deny rules on macOS;
  checked by `sandbox doctor` everywhere): `~/.aizen`, `~/.ssh`, `~/.aws`, `~/.azure`,
  `~/.kube`, `~/.docker`, `~/.gnupg`, `~/.git-credentials`, `~/.netrc`, `~/.npmrc`,
  `~/.config/gcloud`, `~/.config/gh`, browser profiles.

Extra roots come from `sandbox.read_only_roots` / `sandbox.writable_roots`. Paths are handled as
kernel objects (Landlock rules bind to opened directory fds; Seatbelt subpaths are canonical), so
`..`, symlinks and case games do not widen the policy on the enforcing platforms. On Windows the
policy is advisory only — stated plainly by `sandbox status`.

If the workspace is a filesystem root, the home directory, or a system directory, `strict`
refuses (a workspace-write sandbox over `C:\` protects nothing) and `auto` warns; override with
`sandbox.dangerous_allow_broad_workspace = true` if you accept that.

**Git persistence surfaces**: every internal git command Aizen runs (time-machine checkpoints,
repo probing, the writer lease) is hardened with `core.hooksPath` pointed at a nonexistent
directory, `core.fsmonitor=false`, an emptied `credential.helper`, and `GIT_TERMINAL_PROMPT=0` —
a checkout's `.git/hooks` never executes because Aizen made a checkpoint. Git aliases cannot
shadow builtin commands, so aliased-command injection does not apply to internal plumbing.

## Environment isolation

Children never inherit Aizen's environment wholesale. The scrub drops, case-insensitively:

- any name containing `KEY`, `TOKEN`, `SECRET`, `PASSWORD`, `PASSWD`, `CREDENTIAL`, `AUTH`;
- everything under the `AWS_*` and `AIZEN_*` prefixes (`SSH_AUTH_SOCK` falls to the `AUTH` rule).

Everything else (PATH, PATHEXT, SystemRoot, HOME, locale, toolchain homes, …) passes. Known
cost: benign names matching the fragments (`XAUTHORITY`) drop too — restore any specific variable
with `sandbox.pass_env` (exact name or `PREFIX*`). MCP servers receive their **own** configured
env from `mcp.json` on top of the scrubbed base: their tokens are their business; Aizen's are
not inherited. Environment **values** are never written to any log — the audit line carries a
count.

Practical consequence: an agent-run `git push` over SSH will not see your `ssh-agent`
(`SSH_AUTH_SOCK` is scrubbed), and `gh` will not see `GH_TOKEN` from your shell. That is the
sandbox working. If you want those flows to work through the agent, add the variable to
`pass_env` deliberately.

## Network

Default: **deny**. `shell_run` and `process start` accept `network: true|false` (default
`false`); requesting it is a capability escalation — it always surfaces in the approval flow,
`smart` never auto-clears a command that asked for network, and `/yolo` (which only skips
prompts) still gets the caution line printed.

- Linux: enforced by seccomp — `socket(AF_INET/AF_INET6)` returns `EACCES`; UNIX sockets stay
  usable so local IPC and build tooling keep working. A denied `cargo build` that needs to
  download crates fails with a network error: grant `network: true` for that command or vendor
  the deps.
- macOS: enforced by the Seatbelt profile (`(deny network*)`).
- Windows: **unavailable** — no unprivileged kernel mechanism without AppContainer. Not
  pretended otherwise, and there is no fake "domain allowlist": the enforceable unit is
  allow/deny, so that is what the policy speaks.
- Aizen's own network use (LLM calls, Telegram/Discord) is the parent process and is not subject
  to the child sandbox.
- The Docker socket and other out-of-workspace UNIX sockets are covered by the filesystem policy
  on Linux (not in any allowed root ⇒ unreachable).

## Resource limits

Configured under `sandbox.limits`; defaults chosen so real builds don't get surprise-killed:

| limit | default | Linux | Windows |
|---|---|---|---|
| `wall_seconds` | 120 (foreground; `AIZEN_SHELL_TIMEOUT_SECS` overrides) | call-site timer + tree-kill | call-site timer + tree-kill |
| `max_processes` | 256 | `RLIMIT_NPROC` (per-user semantics — kept generous) | Job Object `ActiveProcessLimit` (per-tree, exact) |
| `memory_mb` | unlimited | `RLIMIT_AS` | Job Object memory limit |
| `cpu_seconds` | unlimited | `RLIMIT_CPU` | Job Object per-job user time |
| `max_open_files` | inherited | `RLIMIT_NOFILE` | — |
| `max_file_size_mb` | unlimited | `RLIMIT_FSIZE` | — |
| core dumps | off | `RLIMIT_CORE=0` | n/a |

Foreground commands, background processes, the verify gate and LSP servers all pass through the
same policy system; background processes simply have no wall clock (that is what `process` is
for). Output is already bounded everywhere by the pre-existing ring buffers and drain-grace
timeouts. Tree-kill on timeout/cancel/exit is the pre-existing `proctree` containment (Job
Object kill-on-close on Windows — an Aizen crash reaps the tree too).

## Configuration

```json
{
  "sandbox": {
    "mode": "auto",
    "network": "deny",
    "allow_guarded_fallback": false,
    "read_only_roots": [],
    "writable_roots": [],
    "pass_env": [],
    "limits": { "wall_seconds": 120 },
    "dangerous_allow_broad_workspace": false
  }
}
```

All fields optional; the section itself is optional. `network: "allow"` weakens the default and
is called out by `sandbox status` and `doctor`.

## CLI and REPL surface

- `aizen sandbox status` — the live capability matrix, never inflated;
- `aizen sandbox doctor [--json]` — probes the backend, verifies the audit log is writable, runs
  a real env-scrub self-test (spawns a child, checks a planted secret does not appear), sweeps
  stale private temp dirs, flags risky config;
- `aizen sandbox explain` — how the next `shell_run` would be sandboxed, step by step;
- `aizen sandbox run -- <command>` — run one command under the sandbox by hand;
- `--sandbox auto|strict|guarded|off` on any invocation; `/sandbox` in the REPL.

## Audit log

`~/.aizen/audit/sandbox.jsonl`, owner-only, one line per spawn: timestamp, scope, origin,
command hash (SHA-256/16 hex), the command **redacted** (token shapes replaced) and truncated,
cwd relative to the workspace, requested/effective mode, backend, network grant, count of
scrubbed env vars, degradations, outcome (`exit:N` / `timeout` / `cancelled` / `refused` /
`spawned`), duration. Rotation at ~5 MB to `sandbox.1.jsonl` (one roll kept). Raw secrets,
environment values, and command output are never written. The approval decision itself is not
yet threaded into the record (a spawned command implies it cleared approval); this is listed as
a limitation, not silently omitted.

## Performance

The sandbox adds work only at spawn time: an env filter pass, one small config read, on Linux a
handful of `open(O_PATH)` + Landlock syscalls, on Windows the same Job Object that containment
already created (now with limits), plus one audit line append. Process creation itself dwarfs
all of it; no per-syscall overhead is added on Windows, and seccomp's per-syscall cost on Linux
is a short BPF program. Startup time and binary size are unchanged in kind: no new crates were
added for any of this.

## Known limitations

Stated here so nothing above overclaims:

- **Windows has no kernel filesystem/network sandbox.** An AppContainer backend (workspace ACLs
  granted to a per-profile SID, no network capability, ACL journal + repair) is the designed
  next step but is **not implemented** — Job Object limits + env scrubbing is what ships, and
  `strict` refuses on Windows rather than pretending. Restricted tokens were evaluated and
  rejected for now (they break common toolchains in ways that erode trust faster than they add
  containment).
- Linux seccomp filtering covers the native architecture's syscall numbers (x86_64, aarch64); a
  32-bit multilib child uses a different table and is allowed through rather than broken —
  documented, not hidden.
- On Linux, `RLIMIT_NPROC` counts the user's processes, not the tree's, so the fork-bomb ceiling
  is deliberately generous there; Windows enforces the exact per-tree count.
- macOS `fs_read` is `partial` by design: reads are broadly allowed except the credential
  directories (a full read allow-list breaks system frameworks). `RLIMIT_AS` is not reliably
  enforced by XNU.
- The macOS backend is **not runtime-verified by the maintainer** (no macOS hardware); it is
  exercised by the macOS CI job. The Linux backend is compile-verified against the Linux target
  and its adversarial tests run in Linux CI; treat a first green CI run as the runtime
  verification gate.
- `verify_gate` refusals (e.g. unattended fail-closed) degrade to "no verify ran" — the gate is
  best-effort by contract, so a fail-closed environment silently loses the post-edit compile
  check.
- Approval outcomes are not yet recorded in the audit line (see Audit log).
