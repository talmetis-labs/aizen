# The Aizen sandbox

Aizen runs commands a language model wrote and processes a repository can influence. The sandbox
is the layer that decides **what those processes can reach even if they are malicious** — enforced
by kernel mechanisms where the platform has them, and reported honestly where it does not.

This document is the reference: threat model, architecture, mode semantics, the per-platform
capability matrix, configuration, troubleshooting, and the limitations we know about.

## Desktop document reviews

From a workspace directory, `aizen sandbox review --topic SESSION` reads one JSON request from stdin and prints one JSON reply. Use the saved conversation slug as SESSION. The workspace and topic together scope the ledger. An operator or trusted worker can submit a UTF-8 Markdown document with `{"action":"submit","expected":0,"document":"…","sha256":"…"}`. Compute SHA-256 over the exact UTF-8 bytes. The expected number is the latest version returned by `{"action":"read"}`. This handoff accepts text. VM provisioning has its own lifecycle.

Desktop's Preview offers read, request changes, discard and export for the selected version. Asking for changes records feedback for the producer. Reading an earlier revision uses `{"action":"read","version":1}`. Sample documents are explicitly marked. Export to a chosen folder requires a filesystem supporting hard links. Core checks the digest and records the destination before publication so a retry can reconcile an existing export.

Each document is limited to 64 KiB. Journal admission reserves space for decisions and enforces a 2 MiB per-topic and 64 MiB catalog budget under an OS lock. Discarding a stored version clears its document bytes. User-exported files stay under the destination owner's control.

## Threat model

Protected against (to the degree the capability matrix below says, per platform):

- commands generated by the model (including a model misled by prompt injection in repository
  files, logs, or tool output);
- shell/script indirection: a command that writes a script and runs it, build scripts, test
  scripts, npm lifecycle hooks, Makefiles, Cargo build scripts;
- reading credentials outside the workspace (`~/.ssh`, `~/.aws`, `~/.aizen`, browser profiles,
  cloud credential stores);
- writing or deleting files outside the workspace;
- undeclared network access;
- child/grandchild/background processes escaping cleanup;
- fork bombs, runaway memory, output floods;
- privilege escalation via setuid/capabilities (Linux);
- repository persistence surfaces: `.git/hooks`, fsmonitor daemons, credential helpers are
  disabled for every internal git invocation Aizen makes;
- a sub-agent, workflow, cron job, or hosted bot raising its own privileges — the mode is
  process-global and user-controlled; children inherit, never escalate.

Explicitly **not** protected against:

- kernel exploits;
- an already-compromised user account or machine;
- secrets the user placed **inside** the workspace (the workspace is read-write by definition);
- a human approving a harmful command after reading it.

## Approval is not the sandbox

The two layers answer different questions:

- **Approval** (`ask`/`smart`/`yolo`, plus the `cmd_guard` hard floor): *did the user agree to run
  this command?* `/yolo` skips the approval prompt. It does not touch the sandbox: it grants no
  secrets, no network, no out-of-workspace writes.
- **Sandbox**: *given that the command runs, what can it reach?* Even a fully approved command
  runs without Aizen's secrets in its environment, and — where the kernel backend exists —
  cannot write outside the workspace or open network connections it was not granted.

Execution order for every guarded command: parse → `cmd_guard` hard floor → capability
computation (`network: true` is an escalation and always surfaces) → approval → sandbox policy
resolution → backend capability check (strict fails closed here) → spawn under the sandbox →
audit line.

## Architecture

```
src/sandbox/
  mod.rs           SandboxMode, CommandOrigin, process-wide mode
  policy.rs        config section, env scrubbing, filesystem roots
  request.rs       SandboxRequest — one spawn's worth of intent
  capabilities.rs  the honest per-platform capability probe
  runner.rs        the ONE place a sandboxed Command is built
  audit.rs         owner-only JSONL audit log
  backend/
    guarded.rs     software floor: env scrub, private temp (all platforms)
    linux.rs       Landlock + seccomp + rlimits + no_new_privs
    windows.rs     Job Object limits + containment
    macos.rs       Seatbelt (sandbox-exec) profile
```

Every model- or repository-influenced spawn goes through `runner::prepare_std` /
`prepare_tokio`: `shell_run`, `process start`, the verify gate, LSP servers, MCP stdio servers,
native Memory providers, custom-command `` !`cmd` `` expansion, the REPL `!cmd` escape, and hosted-bot
`/sh`. Call sites
choose a `CommandOrigin`; the model only ever supplies command strings. There is no
`bypass_sandbox` flag, and `InternalTrusted` is constructible only from Aizen's own code with a
literal reason recorded in the audit log.

Internal spawns that do **not** go through the runner, with the reason they are trusted: git
plumbing (`gitx`, hardened as described above — Aizen-controlled argv over untrusted repo data),
`schtasks`/`crontab` registration (fixed argv), `systemctl` service management (fixed argv),
opening the OAuth browser (`start`/`open`/`xdg-open` with a provider URL), and the `ioreg`
device probe on macOS. None of them execute model-supplied strings.

## Modes

| mode | meaning |
|---|---|
| `auto` (default) | strongest available backend. Interactive sessions fall back to `guarded` when no kernel backend exists — warned once per session. **Unattended runs (cron, hosted bots) fail closed** instead, unless `sandbox.allow_guarded_fallback = true`. |
| `strict` | kernel enforcement or refusal. If the platform cannot kernel-enforce the filesystem policy (and network deny, when denying), the spawn is refused before it starts. Never self-downgrades; `/yolo` and remote approvals cannot weaken it. |
| `guarded` | software guards only: approval, `cmd_guard`, env scrubbing, private temp, timeouts, tree-kill, and the resource ceilings the OS offers. Reported as software, never as a kernel sandbox. |
| `off` | the sandbox subsystem stands down: children inherit the full environment and no resource ceilings are applied. The `cmd_guard` hard floor, approval, process-tree containment, timeouts, and the audit log still apply. User-only — no model output can select it. |

Choose the overall level in **`/config` → Sandbox → Mode**, or persist it explicitly:

```sh
aizen config set --sandbox-mode auto     # default: strongest available with interactive fallback
aizen config set --sandbox-mode strict   # kernel enforcement or refusal
aizen config set --sandbox-mode guarded  # software guards only
aizen config set --sandbox-mode off      # no isolation, env scrub or resource ceilings
```

The menu asks for confirmation before choosing `guarded`/`off` or relaxing `strict` to `auto`.
After a successful save, an explicit mode selection also applies to future children in the current
session (including replacing a current session override); it does not resandbox existing processes.
A new invocation resolves `--sandbox <mode>` before `AIZEN_SANDBOX=<mode>`, persisted config, and
finally `auto`. `/sandbox <mode>` changes the current session and saves the default as well.
Network is a separate capability under **Sandbox → Child network**, not the sandbox level itself.

## Platform capability matrix

`aizen sandbox status` prints the live matrix for your machine; this table is the design-level
summary. Levels: **enforced** (kernel), **partial** (kernel for part of the surface),
**advisory** (software checks only), **unavailable**.

| capability | Linux | Windows | macOS |
|---|---|---|---|
| filesystem read confinement | **enforced** (Landlock, 5.13+) | advisory | **partial** (credential dirs denied; other reads allowed) |
| filesystem write confinement | **enforced** (Landlock) | advisory | **enforced** (Seatbelt) |
| network deny | **enforced** (seccomp: `socket(AF_INET/AF_INET6)` → `EACCES`) | **unavailable** | **enforced** (Seatbelt) |
| env isolation (secret scrub) | **enforced** | **enforced** | **enforced** |
| process-tree containment | **enforced** (process groups) | **enforced** (Job Object, kill-on-close) | **enforced** |
| resource limits | **enforced** (rlimits) | **enforced** (Job Object: process count, memory, CPU time) | **partial** (rlimits; `RLIMIT_AS` unreliable on XNU) |

Consequences worth spelling out:

- **On Windows, `strict` refuses every spawn.** There is no unprivileged kernel filesystem or
  network sandbox without an AppContainer backend, which is not implemented (see Known
  limitations). `auto` degrades to `guarded` with a warning; that is the honest ceiling today.
- On Linux kernels without Landlock (< 5.13 or disabled), `auto` degrades and `strict` refuses.
- macOS is probed at runtime (`/usr/bin/sandbox-exec` present and executable); a host without it
  reports `guarded`.

## Native concurrency is not build isolation

In the default direct lane, exact native `read_paths`/`write_paths` capabilities coordinate
cooperating Aizen file tools. Read/read pairs can overlap; a pair containing a writer can overlap
only without write/read or write/write intersections. Capability checks and native resource locks
do not confine arbitrary processes, hooks, external editors or repository build scripts.

Explicit `isolation: "worktree"` uses fresh registered Git-owned roots, not concurrent live
same-file writes in one checkout. Children receive exact bounded native file scopes, not shell/build
access. Actual native worker intents are published before launch; real joins and context-carrier
retirement produce a private release token before the controller may commit attributed paths.
The v2 registration is bounded to 128 workers and 128 KiB of metadata. Source history belongs to Git;
mutation images and attribution remain in the separate native journal. Neither a report nor a
serialized terminal record grants live ownership, restart adoption or physical-settlement proof.
Cancellation, unjoined workers, unknown effects and uncertain publication retain barriers without
automatic retry or cleanup. Destination integration and verification remain separate approved steps.
See [the lifecycle contract](REFERENCE.md#git-owned-native-task-lifecycle).

New `execution: "speculative"` requests are retired, with no implicit direct/Git fallback. Historical
source-store evidence is read by compatibility code, not a source writer or custom same-file merger.
`aizen time recovery --cohort ... --prepared ... --resource ...` uses caller-selected exact resources;
stored paths/IDs are not access or execution authority. Missing roster/lineage, incomplete worker
closure and same-file multi-author records remain diagnostic and unresolved, even for matching
postimages. Default inspection does not append or settle pending guards. Explicit
`--record-observation` only appends bounded nonterminal metadata under fresh parent/writer/physical
admission and existing exclusive ownership; source/native journal bytes and pending barriers stay
unchanged. General crash/unknown-effect reconciliation is not implemented. This does not change the
process capability matrix or imply installation, release or cross-platform acceptance.

Foreground shell/build work stays an opaque exclusive barrier against scoped native editors.
Managed background `process` commands instead retain a separate lifetime barrier, allowing ordinary
sequential tools in the same authorized writer scope to continue while a dev server lives. This is
an explicit compatibility exception, **not filesystem/build isolation**: a background command may
write arbitrary reachable paths while those tools run. Scoped native work, Git-owned native tasks,
native recovery/undo and certified verification remain excluded. Verification coverage
is deferred during that interval; no protected/verified claim is earned. Lost observer/tree proof
blocks ordinary effects with typed uncertainty until actual tree and pipe settlement is proven.

Windows Job Objects provide containment and resource limits, **not filesystem/network isolation**.
Copying the checkout or changing `cwd` does not prevent absolute-path access, inherited handles,
daemon/cache access or IPC escapes.
The ordinary Linux profile retains local IPC and writable host caches; the ordinary macOS
profile permits broad reads. Neither is an isolated-build profile.

No concurrent snapshot-build capability is advertised on any backend. Activating one requires
an owned coherent capture of dirty inputs, complete invocation/environment/toolchain provenance,
private outputs/temp/caches, a dedicated read-denying and escape-resistant policy, and actual
backend/kernel tests before child code runs. Unsupported or unproven enforcement stays exclusive;
`off`, `guarded`, extra user roots or approval cannot authorize unsandboxed overlap. AppContainer
and source ACL changes are not implemented for this purpose.

The parent verifies settled combined edits at the phase boundary rather than treating each
child's report as build evidence. A bounded local source identity rejects detected membership,
content or permission drift, and stale/unsettled passes cannot clear verification. It excludes
output/dependency stores, lacks external/environment/toolchain provenance and uses cooperative
elapsed-time checks, not a hard deadline for blocking filesystem calls. It is live-tree drift
detection, not a coherent snapshot, hostile-race isolation or a reusable build cache key.

## Filesystem policy

Default profile: **workspace-write**.

- read+write: the workspace root, the command's `cwd`, a **private per-run temp directory**
  (`TMP`/`TEMP`/`TMPDIR` point at it; deleted when the run's bookkeeping is dropped), and the
  build-cache homes toolchains write to as a matter of course (`$CARGO_HOME`/`~/.cargo`,
  `~/.npm`, `$XDG_CACHE_HOME`/`~/.cache`);
- read+execute: system and toolchain roots (`/usr`, `/etc`, `/opt`, `~/.rustup`, `~/.gitconfig`,
  `~/.config/git`, …);
- denied (kernel-denied on Linux by omission from the allow-list; explicit deny rules on macOS;
  checked by `sandbox doctor` everywhere): `~/.aizen`, `~/.ssh`, `~/.aws`, `~/.azure`,
  `~/.kube`, `~/.docker`, `~/.gnupg`, `~/.git-credentials`, `~/.netrc`, `~/.npmrc`,
  `~/.config/gcloud`, `~/.config/gh`, browser profiles.

Extra roots come from `sandbox.read_only_roots` / `sandbox.writable_roots`. Paths are handled as
kernel objects (Landlock rules bind to opened directory fds; Seatbelt subpaths are canonical), so
`..`, symlinks and case games do not widen the policy on the enforcing platforms. On Windows the
policy is advisory only — stated plainly by `sandbox status`.

If the workspace is a filesystem root, the home directory, or a system directory, `strict`
refuses (a workspace-write sandbox over `C:\` protects nothing) and `auto` warns; override with
`sandbox.dangerous_allow_broad_workspace = true` if you accept that.

**Read-only Git inspection** uses fixed arguments through the sandbox/settlement boundary and
disables external diff/textconv, fsmonitor and interactive credential prompts. Repository probing
through the hardened resolver is distinct from approved mutations. Git aliases cannot shadow
builtin commands. There is no checkpoint persistence backend or automatic snapshot capture.

**Explicit Git workspace operations** use a separate mutation path, preserving configured
hooks/signing/filters rather than silently bypassing failures. `/time` exposes inspection,
create/remove, explicit branch switch/revert and fast-forward-only integration; it does not yet
provide focus/rebinding or a complete multi-agent Git handoff lifecycle. `work new`
freezes a full committed OID, validates/reserves a new destination, and uses `GitMutation` through
`runner::prepare_std`; configured checkout hooks/filters are not suppressed. Its request uses the
source repository as workspace and the newly reserved directory as `cwd` (Git receives `-C` for
source selection). Ordinary workspace/cwd/cache grants still apply; this is not an exact two-root
sandbox or a repository-independent checkout. Shared Git directories outside these grants can be
refused by enforcing backends. The protected `~/.aizen` root can also prevent managed worktrees
there on enforcing backends; no deny rule is removed to make creation work. Windows strict still
refuses unsupported kernel confinement. Guarded mode remains advisory, including for hooks.
Creation retains cooperative writer/background ownership through actual process settlement and
postinspection. Failed hooks or incomplete verification leave possible partial state for inspection,
not automatic rollback/deletion. Path witnesses detect observed directory replacements but do not
provide atomic exclusion against external filesystem/Git writers. Worktree-creation fixtures target
Windows guarded mode; Linux/macOS enforcement remains unverified.

## Native Memory provider policy

Memory plugins are potentially untrusted native executables, not ordinary workspace build tools.
Installation, eligibility and explicit executable consent are separate; none of them alone starts a
provider. Disabled or unselected Memory starts no provider. Package integrity pins do not establish
publisher trust. The selected executable launches through `runner::prepare_tokio` and contained spawn,
not a shell or a PATH lookup. Full package/protocol details: [Memory plugins](MEMORY_PLUGINS.md).

The request carries a **restrictive override**, not the generic workspace-write profile below:

- Read-only package root; read-write provider data and one private transaction temp directory.
  Fixed platform runtime/library reads are included. No ambient workspace, toolchain/build-cache or
  extra user-configured writable roots are inherited. The policy can represent explicit local-model
  read roots, but the current runtime supplies no additional model roots.
- A strict environment allowlist of host-generated paths/platform constants: synthetic HOME and
  USERPROFILE, temp/config/cache paths beneath the private root, fixed locale and required Windows
  platform directory values. No inherited PATH, `sandbox.pass_env`, API keys, full Core config,
  proxy credentials or toolchain homes. Explicit bounded identity/context is sent in the protocol.
- Network requires **all three**: package declaration, saved manifest-bound executable network grant,
  and global child-network `allow`. Global allow is not a plugin grant; global deny is not overridden
  by the saved plugin grant. These are policy checks, not network enforcement on guarded backends.
- Sandbox `off` is refused for these requests. Strict still refuses unsupported kernel confinement.
  An `auto` backend with partial filesystem/network enforcement is refused rather than silently
  claiming the restrictive roots are enforced. A guarded fallback additionally needs saved informed
  consent for the package; ordinary unattended fallback policy still applies.

**Windows guarded is not filesystem/network isolation.** Job Objects/resource limits and environment
controls do not stop a malicious provider reading/writing files or networking as the current user.
`--allow-guarded` acknowledges that limitation, not a secret-safe sandbox guarantee. Linux/macOS
provider runtime behavior has not been locally verified; the generic matrix is not a passing plugin
test on those platforms.

All provider calls, including searches that may reinforce/cache, use serial opaque admission. A
bounded actor owns one transaction-lifetime process: initialize → one operation → shutdown/drain.
Capacity, exclusive sidecar admission, workspace/physical ownership and activation generation remain
held through process-tree exit and pipe settlement. A reply, timeout, requested kill or dropped future
is not settlement proof. Uncertain cleanup retains a physical recovery barrier; switching/disabling
must not silently redirect queued work or release it. Optional context failures may continue without
Memory only when physically settled. Learning receipts/outbox inventory are independent of this
barrier and cannot clear it. See [current verification](MNEMOS_VERIFICATION.md) for actual Windows
coverage and unverified crash/platform cases.

### Explicit legacy adoption

The `legacy_adoption_v1` and `legacy_adoption_v2` declarations advertise versioned offline migration
facilities, not ordinary provider-context grants. A human-reviewed adoption invocation still requires the selected, enabled,
pinned package and executable consent. It has no network or host-model grant even when broader
permissions were saved for ordinary Memory work.

Adoption uses a dedicated restrictive path policy: package, explicitly selected source and immutable
plan are read-only; only one new operation envelope and private temp are writable. It never receives
write access to the old store, current provider store, HOME, the chosen external parent or the whole
managed namespace. The destination and journal are fresh siblings inside the envelope. Host plans,
operation records and published-root registration are kept separately from provider-writable data.
Normal calls after an explicit storage switch receive only the registered data leaf, not its backup.
V2 preview receives an exact host-authored attachment authorization file through the existing read-only
plan slot, outside its writable envelope. It does not gain write access to host records or broader
filesystem roots. Streaming backup bounds do not enlarge IPC or process deadlines. Reports are accepted
only after zero exit and proven tree/pipe settlement; raw stderr never supplies a public diagnostic.

Offline status does not execute a provider. An interrupted import with confirmed physical settlement
may be resumed explicitly; an unresolved process tree remains a recovery barrier. Adoption recovery
cannot bypass an unrelated provider transaction marker. Source drift, missing receipts and unknown
settlement are not interpreted as success or permission to replay. The Windows guarded limitations
above apply unchanged to adoption. See [the migration workflow](MEMORY_PLUGINS.md#transferring-legacy-aizen-memory).

## Environment isolation

For ordinary sandboxed children, the scrub drops, case-insensitively (native Memory providers use
the stricter allowlist above; ordinary `off` mode bypasses the scrub):

- any name containing `KEY`, `TOKEN`, `SECRET`, `PASSWORD`, `PASSWD`, `CREDENTIAL`, `AUTH`;
- everything under the `AWS_*` and `AIZEN_*` prefixes (`SSH_AUTH_SOCK` falls to the `AUTH` rule).

Everything else (PATH, PATHEXT, SystemRoot, HOME, locale, toolchain homes, …) passes. Known
cost: benign names matching the fragments (`XAUTHORITY`) drop too — restore any specific variable
with `sandbox.pass_env` (exact name or `PREFIX*`). MCP servers receive their **own** configured
env from `mcp.json` on top of the scrubbed base: their tokens are their business; Aizen's are
not inherited. Environment **values** are never written to any log — the audit line carries a
count.

Practical consequence: an agent-run `git push` over SSH will not see your `ssh-agent`
(`SSH_AUTH_SOCK` is scrubbed), and `gh` will not see `GH_TOKEN` from your shell. That is the
sandbox working. If you want those flows to work through the agent, add the variable to
`pass_env` deliberately.

## Network

Default: **deny**. `shell_run` and `process start` accept `network: true|false` (default
`false`); requesting it is a capability escalation — it always surfaces in the approval flow,
`smart` never auto-clears a command that asked for network, and `/yolo` (which only skips
prompts) still gets the caution line printed.

Change the child-network default in **`/config` → Sandbox → Child network** (also available through
`aizen config`), or explicitly persist it from the CLI:

```sh
aizen config set --sandbox-network deny   # default: per-command network:true grants
aizen config set --sandbox-network allow  # broader ordinary-child default; not a Memory plugin grant
```

`allow` does not approve the command itself or disable the sandbox/hard command guard. The menu
requires confirmation before widening the default. Changes apply to newly started children, not
already running servers. Port binding for a dev server also needs network capability. This setting
does not control Aizen's own provider/API or web-search connections. `deny` is not a non-overridable
ban: an approved `network:true` command may still use the network. Kernel deny also requires a
supporting backend in `auto`/`strict`; `guarded` and `off` do not enforce network isolation.

- Linux: enforced by seccomp — `socket(AF_INET/AF_INET6)` returns `EACCES`; UNIX sockets stay
  usable so local IPC and build tooling keep working. A denied `cargo build` that needs to
  download crates fails with a network error: grant `network: true` for that command or vendor
  the deps.
- macOS: enforced by the Seatbelt profile (`(deny network*)`).
- Windows: **unavailable** — no unprivileged kernel mechanism without AppContainer. Not
  pretended otherwise, and there is no fake "domain allowlist": the enforceable unit is
  allow/deny, so that is what the policy speaks.
- Aizen's own network use (LLM calls, Telegram/Discord) is the parent process and is not subject
  to the child sandbox.
- The Docker socket and other out-of-workspace UNIX sockets are covered by the filesystem policy
  on Linux (not in any allowed root ⇒ unreachable).

## Resource limits

Configured under `sandbox.limits`; defaults chosen so real builds don't get surprise-killed:

| limit | default | Linux | Windows |
|---|---|---|---|
| `wall_seconds` | 120 (foreground; `AIZEN_SHELL_TIMEOUT_SECS` overrides) | call-site timer + tree-kill | call-site timer + tree-kill |
| `max_processes` | 256 | `RLIMIT_NPROC` (per-user semantics — kept generous) | Job Object `ActiveProcessLimit` (per-tree, exact) |
| `memory_mb` | unlimited | `RLIMIT_AS` | Job Object memory limit |
| `cpu_seconds` | unlimited | `RLIMIT_CPU` | Job Object per-job user time |
| `max_open_files` | inherited | `RLIMIT_NOFILE` | — |
| `max_file_size_mb` | unlimited | `RLIMIT_FSIZE` | — |
| core dumps | off | `RLIMIT_CORE=0` | n/a |

Foreground commands, background processes, the verify gate and LSP servers all pass through the
same policy system; background processes simply have no wall clock (that is what `process` is
for). Output is already bounded everywhere by the pre-existing ring buffers and drain-grace
timeouts. Tree-kill on timeout/cancel/exit is the pre-existing `proctree` containment (Job
Object kill-on-close on Windows — an Aizen crash reaps the tree too).

## Configuration

```json
{
  "sandbox": {
    "mode": "auto",
    "network": "deny",
    "allow_guarded_fallback": false,
    "read_only_roots": [],
    "writable_roots": [],
    "pass_env": [],
    "limits": { "wall_seconds": 120 },
    "dangerous_allow_broad_workspace": false
  }
}
```

All fields optional; the section itself is optional. `network: "allow"` weakens the default and
is called out by `sandbox status` and `doctor`.

## CLI and REPL surface

- `aizen sandbox status` — the live capability matrix, never inflated;
- `aizen sandbox doctor [--json]` — probes the backend, verifies the audit log is writable, runs
  a real env-scrub self-test (spawns a child, checks a planted secret does not appear), sweeps
  stale private temp dirs, flags risky config;
- `aizen sandbox explain` — how the next `shell_run` would be sandboxed, step by step;
- `aizen sandbox run -- <command>` — run one command under the sandbox by hand;
- `--sandbox auto|strict|guarded|off` on any invocation; `/sandbox` in the REPL.

## Audit log

`~/.aizen/audit/sandbox.jsonl`, owner-only, one line per spawn: timestamp, scope, origin,
command hash (SHA-256/16 hex), the command **redacted** (token shapes replaced) and truncated,
cwd relative to the workspace, requested/effective mode, backend, network grant, count of
scrubbed env vars, degradations, outcome (`exit:N` / `timeout` / `cancelled` / `refused` /
`spawned`), duration. Rotation at ~5 MB to `sandbox.1.jsonl` (one roll kept). Raw secrets,
environment values, and command output are never written. The approval decision itself is not
yet threaded into the record (a spawned command implies it cleared approval); this is listed as
a limitation, not silently omitted.

## Performance

The sandbox adds work only at spawn time: an env filter pass, one small config read, on Linux a
handful of `open(O_PATH)` + Landlock syscalls, on Windows the same Job Object that containment
already created (now with limits), plus one audit line append. Process creation itself dwarfs
all of it; no per-syscall overhead is added on Windows, and seccomp's per-syscall cost on Linux
is a short BPF program. Startup time and binary size are unchanged in kind: no new crates were
added for any of this.

## Known limitations

Stated here so nothing above overclaims:

- **Windows has no kernel filesystem/network sandbox.** An AppContainer backend (workspace ACLs
  granted to a per-profile SID, no network capability, ACL journal + repair) is the designed
  next step but is **not implemented** — Job Object limits + env scrubbing is what ships, and
  `strict` refuses on Windows rather than pretending. Restricted tokens were evaluated and
  rejected for now (they break common toolchains in ways that erode trust faster than they add
  containment).
- Linux seccomp filtering covers the native architecture's syscall numbers (x86_64, aarch64); a
  32-bit multilib child uses a different table and is allowed through rather than broken —
  documented, not hidden.
- On Linux, `RLIMIT_NPROC` counts the user's processes, not the tree's, so the fork-bomb ceiling
  is deliberately generous there; Windows enforces the exact per-tree count.
- macOS `fs_read` is `partial` by design: reads are broadly allowed except the credential
  directories (a full read allow-list breaks system frameworks). `RLIMIT_AS` is not reliably
  enforced by XNU.
- The macOS backend is **not runtime-verified by the maintainer** (no macOS hardware); it is
  exercised by the macOS CI job. The Linux backend is compile-verified against the Linux target
  and its adversarial tests run in Linux CI; treat a first green CI run as the runtime
  verification gate.
- `verify_gate` refusals (e.g. unattended fail-closed) degrade to "no verify ran" — the gate is
  best-effort by contract, so a fail-closed environment silently loses the post-edit compile
  check.
- Approval outcomes are not yet recorded in the audit line (see Audit log).
